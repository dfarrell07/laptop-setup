# Working agreements

- Carry authorized work through implementation and verification. Resolve routine
  reversible choices; ask concrete questions when missing information changes the result.
- Use plain, concise language. Lead with the outcome and report material limitations.
- Verify plans against current code and primary sources. Link to the owning notes
  instead of repeating them; keep instructions accurate and small.
- Use each repository's Make targets and required checks, including slow prerequisites.
- Use feature branches by default and commit logical changes as you go with
  `--signoff` (`-s`). Follow explicit repository workflows and user authorization
  for publishing; a printed push/deploy command is not permission to execute it.
- Preserve existing local work. Keep credentials, private infrastructure details,
  conversation history and personal attribution out of public commits and PR prose.
- Capture durable machine changes in the laptop-setup automation. Locate its
  checkout rather than assuming a fixed home-directory path.
- Keep reusable skills in their owning repositories. Promote verified lessons into
  the appropriate instructions or tests; keep project facts and publishing exceptions local.
- Before large downloads/builds, check free space and whether scratch storage is
  memory-backed. Use a suitable disk-backed workspace for large caches/artifacts.
